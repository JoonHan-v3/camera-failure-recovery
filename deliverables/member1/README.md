## Methodology
The procedure, in the order it was carried out. Details are in the numbered sections below.

1. **Freeze the inputs.**
   * Model: the released BEVFormer-tiny R50 checkpoint (sha256 in MODELS.md), run unmodified at BEVFormer @66b65f3 with
     mmdet3d v0.17.1.
   * Scenes: the frozen pilot set (10 train scenes, 402 samples) and the full nuScenes validation set (150 scenes,
     6,019 samples).
   * Info files: built by the upstream converter restricted to those scenes (`build_infos.py`). The builder runs a CAN-bus
     causal audit as a guard and rejects any info file that fails it (§6).
   * Hashes: recorded for every input (checkpoint, info files, outage code and schedules) in `run.json`.
2. **Use one shared outage definition.** Member 2's frozen schedules and corruption, audit and state code are copied
   byte-identical, so BEVFormer and StreamPETR see the same physical outage.
   * Start: t_start = CAM_FRONT sensor timestamp of keyframe 6.
   * Durations: 0.5, 1 and 2 s.
   * Window: half-open `[t_start, t_start+d)`, compared in exact integer µs.
   * Effect: every CAM_FRONT image in the window is replaced by black. The other five cameras are never touched.
3. **Inject the outage on raw pixels.** The `OutageFrontCamera` step runs right after the images are loaded, before
   normalization, resizing, padding and the backbone. Camera timestamps come from nuScenes `sample_data` and are added by the
   runner, because upstream drops them (§3).
4. **Control the recurrent state.** BEVFormer carries the previous frame's BEV map (`prev_bev`) from one frame to the next.
   * Reset: the runner resets this state before every run.
   * Guard: the model guard requires `prev_bev is None` at the first frame of every scene and fails the run otherwise.
   * Separation: each condition runs in its own process, with batch 1 and no workers, in timestamp order with contiguous
     scenes (§4).
5. **Run the matrix.** On each split there are 5 runs: clean twice, then 0.5, 1 and 2 s outages.
   * Settings: fp32 with TF32 off.
   * Predictions: all 300 decoded boxes per sample are kept, in the common prediction format shared with StreamPETR.
   * Audit: every image the model consumed is logged (§2).
6. **Verify the inputs, independently of the model.**
   * Audit check: each run's audit is compared with the expected manifest and black-image counts recomputed from the raw
     nuScenes JSON (`verify_runs`).
   * Probes: pipeline output tensors are checked on CPU, and a GPU hook checks the tensor the ResNet backbone actually
     receives.
   * Cross-model check: the consumed and blacked image sets are confirmed identical to StreamPETR's.
   * Unit tests: 54 (§5.1–5.3, 5.6).
7. **Verify the model's behaviour.**
   * Repeatability: the two clean runs must be bit-identical.
   * Prefix and post-start: predictions before the outage must be identical to clean, and every prediction after the
     start must change.
   * Isolation: real-model tests show each scene run alone equals the continuous run, with negative controls (a forced state
     leak and no reset) that must be detected.
   * Code regression: after each change to the runner, the pilot clean run is repeated and must match (§5.5, 5.8).
8. **Evaluate with the official metric against a pre-declared gate.** The pass/fail criterion was written down before the
   result was seen: |ΔNDS| and |ΔmAP| ≤ 0.010 against the published 0.354 / 0.252.
   * Clean run: scored with the official nuScenes detection evaluation (upstream `dataset.evaluate`).
   * Outage runs: whole-sequence metrics are reported descriptively, with no significance claim.
   * Diagnostic: a label-free prediction-difference measure by restoration offset (§5.4, 5.7).

   Event-level recovery, thresholds and bootstrap are not part of this method (Members 3/4).
9. **Qualify a backup.** BEVFormer-tiny_fp16 is run through the same adapter, audit and reset, against its own pre-declared
   gate (§5.10).
10. **Inventory data and plan storage.**
    * Inventory: every file in the raw v1.0-trainval JSON is reconciled against disk.
    * Manifests: the exact image set each loader needs is derived. BEVFormer and StreamPETR are taken from real runs;
      SparseBEV is a replication of its pinned selection logic.
    * Storage: outputs are measured per run and the storage plan is set from those numbers (`STORAGE_PLAN.md`).

## 3. Adapter: where and how the outage is applied (verified on the pinned code)
* BEVFormer test pipeline: `LoadMultiViewImageFromFiles(to_float32)` → **`OutageFrontCamera`** → `NormalizeMultiviewImage` →
  `RandomScaleImageMultiViewImage(0.5)` → `PadMultiViewImage(32)` → format/collect. So the black image is inserted on raw decoded
  pixels, before normalization, resize, padding and the backbone (plan p.2).
* Upstream `get_data_info` drops camera timestamps. The runner adds `img_timestamp` = `info['cams'][cam]['timestamp']` (nuScenes
  `sample_data.timestamp`, integer µs) and `eval_ts_us` = sample timestamp; the adapter runs with `ts_mode='abs_us'`
  (exact integers; float seconds would lose µs at 1.5e15). Camera order = converter order (CAM_FRONT = slot 0); filenames are
  cross-checked against the info for every frame.
* BEVFormer consumes **keyframes only** (6 cameras/sample, no sweeps). Its history is the recurrent `prev_bev`, so an outage
  frame contaminates all later frames through the state, not through re-reading old images. Historical images keep their own
  status by construction (each image is decoded once at its own timestamp).
* Iteration: dataset order = timestamp order; scenes verified contiguous (assert); one process, no workers, batch 1, so
  no cross-scene mixing; `SceneStateGuard` additionally rejects any revisited scene / non-increasing timestamp.

## 4. Model state (BEVFormer `prev_frame_info`)
* Upstream resets `prev_bev` only when the scene token changes and **never between runs**. Measured hazard (isolation, control
  c): re-running a scene without a reset reuses the stale BEV at the first frame and changes predictions (max diff 98.7).
* The runner therefore calls `Runner.reset()` before every run (restores `{prev_bev: None, scene_token: None, prev_pos: 0,
  prev_angle: 0}`) and verifies it via `reset_between_runs` (fails otherwise).
* The real state is observed in the inference process by wrapping `simple_test`: at every frame the `prev_bev` actually passed
  to the head is logged; the model guard requires `prev_bev is None` at the first frame of every scene (else
  `StateResetError`), and `run.json` records that `prev_bev` is present on every later frame (temporal mode really used).
* No feature cache exists across conditions: each condition is a separate process and every frame recomputes features from
  the (possibly corrupted) pixels.

## 6. Causality, timing and limitations
* Causal policy = Member 2's frozen alignment allowance (image ts ≤ sample ts + 50 ms); BEVFormer consumes only the six keyframe
  images of the current sample (observed skew −46.1 ms … +1.9 ms on the pilot), no future frames; recurrent state only from
  earlier samples. CAN bus: the upstream converter takes pos/orientation from the *latest pose message at or before* the sample
  time, but copies the 9 auxiliary values (accel, rotation rate, velocity; 3 each) from the *first message after* it
  (`can_bus.extend(pose[key])` uses the loop variable). At inference `get_data_info` overwrites pos/orientation/yaw with the ego
  pose, so the CAN values that reach the model (`can_bus_mlp`) are exactly those 9 auxiliary values. **Audited for every info**
  (`outage/canbus_audit.py`, tied to the info sha256): offsets +32 µs … +37.7 ms (pilot), −7.4 ms … **+49.9 ms** (val); 0 values
  over the frozen sample+50 ms allowance; all values match the selected message. So BEVFormer inference is compatible with the
  declared sample+50 ms availability allowance — **not** with strict availability at the sample time, and no zero-latency claim
  is made. `build_infos.py` now runs this audit as a guard and rejects regenerated infos that exceed the allowance. The upstream
  behaviour is kept because the released model was trained with it.
* Missing follow-up bins come from the shared schedule/keyframe spacing (same scenes as Member 2); they are reported, not hidden.
* Environment deviations from upstream install doc: numpy 1.19.5 (as documented), nuscenes-devkit 1.1.9, numba 0.48.0,
  pillow<10, detectron2 recent commit (import only), mmdet3d CUDA ops built with nvcc 11.8 / g++-11 for sm_86. The baseline gate
  is the check that these do not change results.
* Latency in `run.json` is synchronized per-frame end-to-end time including JPEG decode, with 3-4 concurrent processes and no
  warm-up discarded — not the isolated warmed-up batch-one GPU latency (Member 4's profiling).
* Missing follow-up bins break only the adjacent recovery-confirmation pair containing them; later valid pairs remain usable;
  unknown follow-up is never classified as permanent failure (shared rule, Member 2's `audit.missing_bins`).
