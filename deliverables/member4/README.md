## Methodology
The procedure, in the order it was carried out. Details are in the numbered sections below.

1. **Take the frozen inputs, read-only.** Per-scene / per-phase statistics of all three models from Member 3 (`SparseBEV/artifacts/event_stats`, geometry v2),
   the frozen per-model score thresholds, the shared outage schedule, and the packaged GT tables. Their hashes are stored with the results.
   Event rules were frozen *before* any validation event statistic existed: damage if pooled recall loss during the outage > 0.05 with ≥ 5 eligible objects;
   recovery onset = first post-restoration bin with loss ≤ 0.05 whose next adjacent bin also qualifies; a missing or insufficient bin breaks the pair.
2. **Check the runs before using them** (§2): all 12 validation runs and the pilot / second-clean runs are integrity-checked against their own `run.json`,
   `audit.json`, checkpoint on disk, TF32 flags, expected sample and black-image counts; the validation schedule must be byte-identical across projects.
3. **Verify Member 3's tables independently.** Every (scene, duration, phase) cell is rebuilt from the per-sample statuses with this project's own phase
   assignment and counting (64,350 cells per model) and compared with the CSVs. Pooled estimates are also compared with Member 3's own summaries.
4. **Pooled recovery curves.** Per phase, recall is pooled over the *same* eligible objects of the paired clean and outage runs; loss L = R_clean − R_outage,
   plus relative loss, precision and false positives. Models share ground truth and eligibility, so denominators are identical across models (asserted).
5. **Paired scene bootstrap.** Complete scenes are resampled with replacement; one weight matrix is used for all three models and all durations, so clean/outage
   pairing, within-scene dependence and cross-model pairing are preserved; every statistic is recomputed in every replicate from saved per-scene counts (no new
   inference). B = 10,000, seed 535, percentile 95% intervals.
6. **Aggregate degradation rule** (plan p.4): "detected" only if pooled loss during the outage > 0.05 *and* the interval excludes zero; otherwise the wording is
   "no statistically detected aggregate degradation". Aggregate-curve recovery onset is kept separate from per-event recovery.
7. **Per-event categories**: insufficient data; no measured degradation; damaged with recovery at the first observed bin; damaged with later recovery; damaged
   without confirmed recovery under *complete* follow-up; damaged and *unconfirmed because follow-up is incomplete* (right-censored — never read as permanent
   failure). Reported: the full curve, the fraction of damaged events with confirmed onset by 4 s with censored events kept in the denominator, a recovery-time
   median only when reached (its 95% interval uses ALL 10,000 replicates; replicates in which the median is not reached are kept as +∞, so an upper endpoint
   can be "not reached"), and recovery among events with complete follow-up (a selected subset, reported as an observed association).
8. **Common-event comparison and paired differences** between models (damage rate, pooled loss, confirmed-onset fraction on events damaged in all three models).
9. **Diagnostics**: per-class recall loss and a same-object diagnostic that follows eligible GT instance tokens from the last during-outage sample to the first
   *strictly later* sample whose CAM_FRONT exposure is restored (continuing errors vs objects entering/leaving the region). A sample can be both the last "during"
   sample (black front exposure, by sensor time) and bin 0.0 (by evaluation time); such zero-time or still-black pairs are counted as unavailable, never as recovery.
10. **Resource profile** of each released detector in its own environment with its own study runner: pristine input templates pre-built, a FRESH deep copy for every
    forward including warm-up (made outside the timed region, because upstream forwards edit their metadata in place), one discarded warm-up pass, three measured passes with
    CUDA synchronization around every frame, peak allocated memory reset after warm-up; input-identity and output-repeatability checks recorded; CPU decode/pipeline time
    separate, and end-to-end time measured as paired per-frame totals (that frame's decode + that frame's forward).
11. **Figures** from the saved analysis only; qualitative events chosen by fixed rules (not by eye).
12. **Reproduce results** from the saved configuration: the pilot 2 s outage of each model is re-run by the member project's own runner into a scratch
    directory and compared bit-for-bit with the saved run (predictions, audit records, checkpoint hash).

## 2. How to run
```bash
export PATH=$HOME/anaconda3/envs/sparsebev/bin:$PATH          # numpy / scipy / matplotlib only; no GPU needed except profiling and reproduction
cd RecoveryAnalysis
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s . -t . -p 'test_*.py'        # 23 tests
python3 -m recovery.orchestrate status           # integrity of all runs -> artifacts/run_manifest.json, RUN_SUMMARIES.md
python3 -m recovery.orchestrate execute          # dry run: lists missing validation runs (none); --run launches them via the member projects, <= 2 GPU processes
python3 -m recovery.orchestrate all              # status -> verify_tables -> analysis -> deep_dive -> figures   (the single evaluation command)
python3 -m recovery.qualitative                  # qualitative gallery
artifacts/run_profile.sh                         # resource profile of the three models (each in its own env; GPU must be idle)
python3 -m recovery.orchestrate reproduce <sparsebev|bevformer|streampetr> pilot 2     # one result re-run from the saved configuration (GPU)
python3 -m recovery.orchestrate recompare <model> pilot 2                              # re-run only the comparison on an existing scratch reproduction
python3 -m recovery.collect_deliverables         # -> ../deliverables/member4 (+ SHA256SUMS)
```
Models are always run by their own project's runner (`SparseBEV/outage/run_sparsebev`, `BEVFormer/outage/run_bevformer`, `StreamPETR/outage/run_streampetr`); the
orchestrator never duplicates inference code. Seeds: bootstrap seed 535 (B = 10,000); inference is deterministic (batch 1, TF32 off, fixed seeds in each project).

## 3. Results (full validation, 150 scenes; descriptive, with paired scene-bootstrap 95% intervals)
Operating points: per-model thresholds frozen on the pilot scenes (SparseBEV 0.542, StreamPETR 0.758, BEVFormer 0.879; precision ≈ 0.95–0.995 at recall ≈ 0.30–0.32).
Clean front-region recall before the outage differs across models (SparseBEV 0.34, StreamPETR 0.31, BEVFormer 0.26), so absolute losses are not directly comparable;
the **relative** loss (share of clean recall lost) is reported next to them.

| outage | model | pooled loss during (95% CI) | relative loss during | loss in first bin (0.0 s) | aggregate degradation |
|---|---|---|---|---|---|
| 0.5 s | SparseBEV | 0.145 (0.119, 0.170) | 0.40 | 0.023 | detected |
|  | StreamPETR | 0.093 (0.068, 0.116) | 0.29 | 0.019 | detected |
|  | BEVFormer | 0.168 (0.141, 0.195) | 0.59 | 0.014 | detected |
| 1 s | SparseBEV | 0.171 (0.143, 0.199) | 0.48 | 0.040 | detected |
|  | StreamPETR | 0.118 (0.096, 0.140) | 0.38 | 0.037 | detected |
|  | BEVFormer | 0.194 (0.170, 0.221) | 0.69 | 0.027 | detected |
| 2 s | SparseBEV | 0.213 (0.187, 0.238) | 0.60 | 0.072 | detected |
|  | StreamPETR | 0.149 (0.125, 0.173) | 0.48 | 0.074 | detected |
|  | BEVFormer | 0.224 (0.198, 0.253) | 0.79 | 0.030 | detected |

1. **Every model loses front-region recall while the camera is black**, increasingly with duration (all intervals exclude zero and the loss exceeds 5 points).
2. **Recovery is fast in the pooled curve.** The aggregate curve is back within the 0.05 margin from the first post-restoration bin for 0.5 s and 1 s outages
   (and for BEVFormer after 2 s); after 2 s outages SparseBEV and StreamPETR are above the margin at 0.0 s (0.072 / 0.074) and below it from 0.5 s. From 0.5 s on, every pooled
   loss stays within ±0.031 (from 1.0 s on within ±0.019). Of the 90 model × duration × bin cells for 0.5–4.5 s, 5 have a 95% interval that excludes zero — about the 4–5 expected by chance
   for uncorrected 95% intervals: two are small *positive* losses at 0.5 s after a 2 s outage (SparseBEV 0.025, StreamPETR 0.031; still below the 0.05 margin) and three are small *negative* losses (outage recall
   slightly above clean: SparseBEV and StreamPETR at 3.0 s after 0.5 s outages, BEVFormer at 2.0 s after 2 s outages).
3. **No step when the history clears.** SparseBEV's predictions stay different from clean until the last black frame leaves its 8-keyframe window (≈ 3.54 s after restoration;
   Member 3), yet the pooled recall shows no measurable loss at 3.0–4.0 s (e.g. 2 s outage, bin 3.5 s: 0.003, interval −0.004…0.010). BEVFormer's recurrent state never
   returns to bit-identical predictions, but its pooled recall loss is also gone from the first bins. Both observations are about *recall at a fixed threshold*, not about score or box quality.
4. **Per-event damage** (among events with ≥ 5 eligible objects during the outage): damage rate SparseBEV 0.66 / 0.71 / 0.74, StreamPETR 0.49 / 0.57 / 0.63, BEVFormer
   0.79 / 0.79 / 0.80 (0.5 / 1 / 2 s). Paired differences: StreamPETR is lower than both (StreamPETR − BEVFormer −0.30 / −0.22 / −0.17, intervals exclude zero; SparseBEV − StreamPETR
   +0.17 / +0.14 / +0.11, intervals exclude zero); SparseBEV vs BEVFormer is not distinguishable (intervals reach zero). The pooled during-outage loss gives the same picture (StreamPETR lowest).
   **This is a descriptive ranking only**: the three systems differ in clean recall, threshold operating point, resolution, pretraining, query count and history; architecture is not isolated.
5. **Per-event recovery fractions are strongly associated with follow-up completeness.** The fraction of damaged events with confirmed onset by 4 s is 0.91 / 0.94 / 0.91 (0.5 s),
   0.77 / 0.75 / 0.78 (1 s) and 0.68 / 0.61 / 0.64 (2 s) for SparseBEV / StreamPETR / BEVFormer, but 44–77 % of damaged events have incomplete follow-up (a missing or insufficient bin from the
   shared keyframe spacing and the frozen ≥ 5 object rule; identical scenes for every model). Under *complete* follow-up, confirmed recovery occurs in 26/26, 19/19, 29/29 (0.5 s),
   27/27, 16/16, 27/27 (1 s) and 22/22, 17/18, 26/26 (2 s) damaged events; no damaged event has complete follow-up and no confirmed recovery except one StreamPETR 2 s event.
   Unconfirmed events are therefore **right-censored, not failures**; the complete-follow-up events are a *selected* subset (every bin has ≥ 5 objects), so this is an observed association and does not
   by itself separate model behaviour from the schedule. Medians of the confirmed onset (censored events kept in the denominator; reached for all; 95% interval from all 10,000 replicates with unreached replicates kept as +∞):
   SparseBEV 0.5 [0.0, 0.5] / 0.5 [0.5, 1.0] / 1.5 [1.0, 2.0] s, StreamPETR 0.0 [0.0, 0.5] / 1.0 [0.0, 1.5] / 2.0 [1.0, 4.0] s, BEVFormer 0.5 [0.0, 0.5] / 0.5 [0.5, 1.0] / 1.0 [0.5, 2.0] s
   (replicates with the median not reached: 0–2 of 10,000, except StreamPETR 2 s with 235 = 2.35 %, which is why its upper endpoint rises from 3.0 s to 4.0 s; correction 1). On the common population of events damaged in all three models (24 / 49 / 70) the onset fractions are 0.92 / 0.76–0.78 / 0.63–0.64
   with no distinguishable model difference.
6. **Same-object diagnostic** (continuing objects the clean run detected at both the last during-outage sample and the first *strictly later sample with a restored front image*, outage run missed during):
   the share detected again is SparseBEV 0.95 / 0.89 / 0.85, StreamPETR 0.87 / 0.80 / 0.70, BEVFormer 0.89 / 0.88 / 0.82 (0.5 / 1 / 2 s; intervals in `classes_sameobject.json`); the rest are persisting
   misses (as a fraction of continuing clean-detected objects: SparseBEV 0.02 / 0.07 / 0.12, StreamPETR 0.05 / 0.11 / 0.21, BEVFormer 0.07 / 0.11 / 0.17). Event accounting: for all 150 events there is a valid pair;
   the later sample is bin 0.0 for 132 / 124 / 115 events and bin 0.5 s for 18 / 26 / 35 (6 / 4 / 6 of these are events where bin 0.0 is the *same sample* as the last during-outage sample; no event has a still-black bin 0.0 that is
   distinct from it); mean later-bin offset 0.06 / 0.09 / 0.12 s. **Correction 3**: the first version compared the same sample with itself in those 6 / 4 / 6 events (counting continuing misses as "persisting after restoration"
   — e.g. recovered share 0.81 / 0.86 / 0.75 for SparseBEV) and left out events with no bin-0.0 sample; the superseded outputs are kept in `artifacts/superseded_before_inspector_review2/`.
7. **Per-class** losses (2 s outage, during) are largest for cars (SparseBEV 0.31, n = 1,220) and smallest for classes with few objects; intervals for rare classes (construction vehicle, trailer; n < 50) are wide and
   flagged `small_denominator` (`fig_per_class_loss.png`).
8. **Resources** (RTX 3060 12 GB, batch 1, TF32 off, warmed up, CUDA-synchronized, 80 frames × 3 passes): median model latency SparseBEV 190 ms (5.3 FPS), BEVFormer 131 ms (7.6 FPS), StreamPETR 79 ms (12.7 FPS, fp16 per
   its config); per-frame CPU decode + pipeline (single process, no workers) 209 / 151 / 152 ms, so measured paired end-to-end (per-frame decode + forward, median) 403 / 284 / 231 ms; peak allocated GPU memory 2,652 / 617 / 375 MB (reserved 2,994 / 756 / 540 MB; each fits
   the 12 GB card with ample margin; one SparseBEV process held ≈ 4.4 GB incl. context in the study runs). Pass medians agree within 4 %. Re-profiled after correction 2 (fresh input copies for every forward): SparseBEV's and BEVFormer's
   forwards edit their inputs in place in 320 / 320 forwards, StreamPETR's in none; all detections are bit-identical across the warm-up and measured passes; the superseded profile (188 / 128 / 78 ms) reused edited inputs.
9. **Official whole-sequence scores** barely move (NDS 0.556→0.552 for SparseBEV after 2 s; `fig_official_metrics.png`): whole-sequence metrics dilute a brief single-camera outage, as the plan anticipated.

## 5. Limitations and caveats (preserve in the report)
* **Per-event analysis is noisy by construction**: 2 Hz keyframes give ~1–5 samples per outage and ~1 sample per bin per scene (≈ 5 eligible objects per sample); the frozen ≥ 5 object rule leaves 80 / 51 / 25 of 150 events insufficient
  (0.5 / 1 / 2 s). With ~5 objects per bin a loss of one object is 0.2, so "loss ≤ 0.05" means in practice "no object lost"; per-event damage is decided on very few objects. The pooled curves are the more reliable summary.
* **Censoring is large in per-event recovery** (item 5): do not compare "fraction recovered by 4 s" across models without the complete-follow-up and common-event rows. Complete-follow-up events are a selected subset (every bin has ≥ 5 objects).
* **Thresholds and clean recall differ across models**; the ranking is descriptive. Thresholds were calibrated on the 10 pilot *training* scenes, which all three released models saw in training.
* **Region ≠ visibility**: the front region is the projection of GT centers inside CAM_FRONT within 50 m; other cameras overlap it, objects may be occluded, and object motion is not compensated to exposure time (plan p.3).
* Scene-bootstrap intervals measure sampling variability over 150 scenes with one deterministic run per condition; they do not include run-to-run inference variance (none exists here: repeatability is bit-exact) nor model/training variance.
* Pairwise intervals are paired scene bootstraps of the stated statistic; non-overlap of two separate intervals (e.g. the relative losses) is **not** a formal test.
* Latency is for batch one on one RTX 3060 shared with a desktop session; the profile excludes CPU decode (reported separately) and the result copy back to CPU; StreamPETR runs fp16 as released (BEVFormer-tiny and SparseBEV fp32). The study runner's observation wrappers
  were left in place (negligible: dictionary lookups; StreamPETR's `observed` hook syncs once per scene start).
* Qualitative events are chosen by fixed rules, which include a no-degradation counter-example; they illustrate, they do not prove, and the "late recovery" example may show mostly objects that neither run detects.
* Official whole-sequence metrics dilute the outage; no significance is claimed from them.
